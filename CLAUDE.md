## Project

Arcade Vault: a retro arcade portal for playing games online and competing on a points leaderboard (see README.md). Next.js 16.3.3 (App Router, TypeScript, React 19, Tailwind CSS v4) + Supabase (Auth + Postgres). UI copy is in Spanish.

Commands: `npm run dev`, `npm run build`, `npm run lint`, `npm run typecheck`, `npm run check` (lint + typecheck), `npm run format`. There is no test runner configured. CI (`.github/workflows/ci.yml`) runs lint, typecheck and build on every PR and push to `main`.

## Architecture

- **Routes (`app/`)**: `/` home, `/about` (contact form → Server Action in `app/about/actions.ts` sending email via Resend), `/auth` (Supabase Auth, actions in `app/auth/actions.ts`), `/biblioteca` (game library), `/salon` (Hall of Fame), `/juegos/[id]` (game detail + top 10), `/juegos/[id]/jugar` (player; `actions.ts` has the `saveScore` Server Action).
- **Pages are thin Server Components** that fetch data and pass it as props to UI components, grouped by screen in `components/`: `layout/` (`Nav`), `shared/` (`GameCard`, `useReveal`), `home/` (`Home` + `HomeFeatures`, `HomeActivity`, `HomePricing`, `FloatingSilhouettes`), `about/`, `auth/`, `library/`, `hall-of-fame/`, `game-detail/`, `player/` (`GamePlayer`, `SkinSwitch`, `useGameSkin`, `TouchPad`) and `games/` (registry + one Canvas per game). Server Actions stay colocated with their route (`app/**/actions.ts`).
- **Supabase clients (`lib/supabase/`)**: `server.ts` (Server Components/Actions, cookie-based, create one per request), `client.ts` (browser), `proxy.ts` (`updateSession`). Root `proxy.ts` (Next 16's replacement for middleware) refreshes the session and redirects logged-in users away from `/auth`.
- **Data layer (`lib/catalog/`)**: `types.ts` (`Game`, `GameStats`, `GameWithStats`, `LeaderboardRow`) and `queries.ts` (server-only: `getGames`, `getGamesWithStats`, `getGame`, `getGameStats`, `getLeaderboard`, `getPlayerBest`). Queries swallow errors and return empty values. `getGames`, `getGamesWithStats` and `getGame` filter by `playable = true`, so unimplemented games are hidden everywhere (Home, Biblioteca, Salón) and `/juegos/[id]` returns 404 for them; a game appears by setting its `playable` flag (the `/add-game` migration). `categories.ts` keeps `CATS`. Shared formatters (`formatScore`, `formatBest`, `formatRank`, `formatScoreDate`, es-ES) live in `lib/format.ts`; don't call `toLocaleString` ad hoc.
- **Database** (`supabase/migrations/`, applied to the remote project via the Supabase MCP): `profiles` (created by `handle_new_user` trigger), `games` (catalog, read-only for clients, changes only via migration; `playable` flag), `scores` (public read; insert only by the authenticated owner on playable games; no update/delete), views `leaderboard` (best score per user/game with `rank`) and `game_stats` (`best`, `plays`), both `security_invoker`. After schema changes regenerate `lib/supabase/database.types.ts` with the MCP `generate_typescript_types`. Each newly playable game gets its own migration (`<timestamp>_<slug>_playable.sql`, e.g. `caida`, `bloque_buster`, `serpentina`). The Supabase MCP server is configured in `.mcp.json`.
- **Games**: engines live in `lib/games/<game>/` as framework-agnostic TS (e.g. `rocas/engine.ts`, folder = `games.id` slug), wrapped by a `<Name>Canvas.tsx` component in `components/games/` and hosted by `components/player/GamePlayer.tsx`, which looks the game up in `GAME_REGISTRY` (`components/games/registry.tsx`). Shared game-platform code is in `lib/games/platform/`: `contract.ts` (`GameStatus`, `GenericHud`, `GameRenderProps`, `GameEntry`, `GameEngine`, `CreateGame`), `skins.ts`, `touch.ts`. Every Canvas is a few lines calling `useGameCanvas(createXGame, props)` (`components/games/useGameCanvas.ts`), which creates the engine once, wires callbacks through refs, applies the skin and maps `status` → `start/pause/resume/reset`. Each `GameEntry` has `Canvas` (receives `status: "ready" | "playing" | "paused" | "over"`, `skin`, `onHud(GenericHud)`, `onGameOver(finalScore)` and `inputRef`), `hud` (subset of `score | lives | level | lines`), `controls`, `startTitle`, `startHint` and a **required** `touch` layout; ids without an entry get the simulated demo. Touch controls (spec 12): every engine exposes `press/release/releaseAll(action)` (its `XAction` union in `types.ts`; the keyboard maps keys → actions and goes through the same functions); the Canvas assigns the engine to `inputRef` (`GameInput`, `lib/games/platform/touch.ts`) and `GamePlayer` renders `components/player/TouchPad.tsx` (D-pad + A/B from `entry.touch`, built with `touchLayout<XAction>()`, `repeat` for hold-to-repeat), calling `releaseAll()` when leaving `playing`. The pad only shows on `@media (pointer: coarse)`, with its own portrait/landscape player layout in `app/styles/player-mobile.css` and `app/styles/touchpad.css`. Its look is the "Gamepad MK-II" (spec 13, reference in `references/gamepad-assets/`): fixed silhouette in every game (4 D-pad keys with SVG arrows + central hub with a gem, B left / A right); slots not declared in `entry.touch` render inert (`aria-disabled`, `data-inert`, no handlers); only A/B show their `label`, as silkscreen text under the button (D-pad labels stay in `aria-label`). `TouchPad` receives `skin` from `GamePlayer` (`data-skin`) and switches between three shared palettes of `--pad-*` CSS variables (`clasico` = MK-II, `neon`, `retro` NES-like); single shell under the CRT on tablet/portrait, two half shells (`.touch-shell`) beside the CRT in landscape. On game over `GamePlayer` calls `saveScore`, so the leaderboard needs no per-game code. Playable so far:
  - `rocas` — Asteroids, `lib/games/rocas/`.
  - `caida` — Tetris, `lib/games/caida/`.
  - `bloque-buster` — Arkanoid, `lib/games/bloque-buster/`, sprites/sounds in `public/games/bloque-buster/`.
  - `serpentina` — Snake, built from scratch in `lib/games/serpentina/`, fruit atlas in `public/games/serpentina/` (source in `references/source-assets/snake-assets/`).
  - `ranaria` — Frogger, built from scratch in `lib/games/ranaria/` (spec `specs/15-ranaria-frogger.md`); 16×14 board of 40 px centered in the 800×600 world, HUD drawn in the side margins, primitives only (no sprites).
  - New games use the `games.id` slug for folder, assets, migration and URL (see the `add-game` skill).
- **References**: original vanilla JS games to port in `references/started-games/`; visual design templates in `references/templates/`; raw art in `references/source-assets/`; table of the currently playable games (id, title, category, short description, color) in `references/implemented-games/implemented-games.md` — update it whenever a game is made playable.
- **Home**: `components/home/` still reads `ACTIVITY` and `TOP_PLAYERS` from `lib/placeholder/home-data.ts` (placeholder data, not Supabase).
- **Styling**: `app/globals.css` only imports Tailwind and the partials in `app/styles/` (their `@import` order is the cascade order): `base` (tokens `--bg`, `--cyan`…), `background`, `frame`, `nav`, `buttons`, `library`, `covers` (`.cover-*`), `detail`, `player` (`.crt-*`, modal), `auth`, `salon`, `misc`, `home`, `about`, `games` (per-game canvas blocks), `leaderboard`, `skin-switch`, `touchpad`, `player-mobile`. Add rules to the partial of their zone, not to `globals.css`; fonts (Press Start 2P, JetBrains Mono, Courier Prime) are set in `app/layout.tsx`.
- **Performance (spec 14)**: heavy global effects do not run under the player. `GamePlayer` sets `data-player` on `<html>` while mounted (cleanup on unmount) and `app/styles/background.css` turns off, under `html[data-player]`, the animated `.av-bg::before` grid and hides `.av-bg::after` and `.av-noise`. New page-level effects must not use `mix-blend-mode`, `backdrop-filter` or full-screen `background-position` animations without being disabled there (the CRT scanlines `.crt-screen::after` are plain black-with-alpha, no blend mode). Decorative animations in the player respect `prefers-reduced-motion` (extend the existing block, don't duplicate it). In `GamePlayer` and the Canvas components, prefer `useRef` over `useState` for values that change per frame/play: the HUD (`score`, `lives`, `level`, `lines`) lives in refs and `paintHud` writes `textContent` directly, `useState` is only for tree-changing state (`status`, `save`, `username`), and callbacks passed to Canvas (`onHud`, `onGameOver`) keep a stable identity. Neon-skin `shadowBlur` is a per-skin cost that page effects can't fix (RANARIA `neon` is under budget, see the spec's Medición).

Env vars (see `.env.example`): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `RESEND_API_KEY`, `SUPABASE_DB_PASSWORD`, and dev-only `DEV_ALLOWED_ORIGINS` (comma-separated LAN IPs for `allowedDevOrigins` in `next.config.ts`, to test on a phone).

Other folders: `docs/game-jam/` (jam results), `references/` (source material only, ignored by ESLint/Prettier), `supabase/migrations/`, `public/games/<slug>/` (game assets).

## Skills

- Use always `/frontend-design` to design the user interface.
- `/add-game` (project skill in `.claude/skills/add-game/`): use it whenever a game is added, ported or made playable. It covers the TS engine, canvas component, registry entry, `playable` migration and leaderboard wiring, with references (`engine-contract.md`, `game-registry.md`, `leaderboard-integration.md`, `porting-vanilla-js.md`) and templates for the spec and the migration.
- `/spec` and `/spec-impl` (user-level skills from `Klerith/fernando-skills`): Spec Driven Design flow, see Workflow.
- `/spec-impl-game <NN-spec>` (project skill in `.claude/skills/spec-impl-game/`): same flow as `/spec-impl` (it reads and follows the user-level skill) for game specs; once the last step is confirmed it launches `skin-designer` and then `mobile-porter`, strictly one after the other, and never commits.
- `/worktree <task>` (user-level skill): runs the task in an isolated git worktree under `.trees/<name>`, on its own branch.
- `/game-jam <tema>` (project skill in `.claude/skills/game-jam/`): runs a game jam on a theme: 3 `game-jam-designer` agents in parallel (A acción, B puzzle, C wildcard/versus) each write a pitch + spec; the main session judges them with `references/rubrica.md`, writes `veredicto.md`, copies the winner to `specs/NN-<id>.md` and logs the ideas in game-planner's memory. Results in `docs/game-jam/<fecha>-<tema>/` (see `docs/game-jam/README.md`).

## Agents

Project subagents live in `.claude/agents/`; each file holds its full definition (tools, contract, procedure). Their per-project memory is in `.claude/agent-memory/<name>/MEMORY.md`. Read the definition file before relying on one.

- `game-planner` — decides which game fits the platform next; read-only, outputs a spec-ready card for `/add-game <id>`. `.claude/agents/game-planner.md`
- `game-performance-booster` — audits/measures one game's performance (fps, frame p95, Paint+Raster, GPU) against spec 14; audit-only unless asked. `.claude/agents/game-performance-booster.md`
- `skin-designer` — ensures every playable game has 3 skins (`clasico`, `neon`, `retro`) and implements missing ones. `.claude/agents/skin-designer.md`
- `mobile-porter` — audits/fixes mobile and responsive UX and the touch pad across a viewport matrix (spec 12/13). `.claude/agents/mobile-porter.md`
- `game-jam-designer` — writes one pitch + spec for a jam; launched by `/game-jam`, not used alone. `.claude/agents/game-jam/game-jam-designer.md`

Run `game-performance-booster`, `skin-designer` and `mobile-porter` after `/add-game` (the last two are chained by `/spec-impl-game`).

## Before writing code

Read `node_modules/next/dist/docs/` first — this project pins Next.js 16.3.3, which has breaking changes vs. older Next.js versions likely present in training data (e.g. typed route props like `LayoutProps<"/">` in `app/layout.tsx`, `proxy.ts` instead of `middleware.ts`). See AGENTS.md above for details; that block is regenerated by `next dev` and should be committed as-is, not stripped out.

A PostToolUse hook (`.claude/hooks/format-and-lint.mjs`) runs Prettier + ESLint --fix on every edited file and strips blank lines from JS/TS/CSS files; unfixable lint errors are reported back and must be fixed.

## Workflow

Per README.md, this project follows Spec Driven Design using `/spec` and `/spec-impl` commands from the `Klerith/fernando-skills` skill pack (installed via `npx skills@latest add Klerith/fernando-skills`). Specs live in `specs/NN-slug.md`, indexed with their status in `specs/README.md` (01–10, 12–15 implemented; 11 `invasores`, 16 `anzuelo` and 18 `oauth-google-github` are drafts; 17 `confirmacion-correo-recuperar-password` is paused (code only on branch `spec-17-…`, not merged; "Confirm email" stays off in Supabase); 01 is used twice for historical reasons); the next free number is 19; `/spec-impl` auto-creates a `spec-NN-slug` branch (`specs/.spec-config.yml`). Prefer that spec → implementation flow over ad hoc changes when adding features.
